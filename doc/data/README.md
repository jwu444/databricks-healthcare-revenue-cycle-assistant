# Dental Practice Synthetic Dataset

20 referentially-integral CSV tables modelling a 20-office dental group practice (MSO) across three benefit years, **2023-09-01 → 2026-08-31**. 50,760 rows total.

Generated by [`../generate_dental_data.py`](../generate_dental_data.py) (seeded, deterministic — re-running reproduces these files exactly). Model: [`../dental_data_model_design.md`](../dental_data_model_design.md), with the corrections below.

All data is synthetic. **No PHI, no real patients, no real practices.**

---

## Corrections to the design doc

Three things in `dental_data_model_design.md` were changed. The first was a genuine contradiction in the source document; the other two are modelling fixes.

### 1. Reminders were backwards — now split into two tables

The ER diagram shows:

```
[ Dental_Offices ] → [ Reminders ] → [ Appointments ]
```

but the doc's own script builds the opposite: a reminder carrying `appointment_id`, sent at `appt_date - 2 days`. **A notice about an appointment that already exists cannot also be the thing that causes it.** The script's reminder also had no `office_id`, so the `Dental_Offices → Reminders` edge in the diagram did not exist in the schema at all.

Both readings describe something real, so they are now separate tables:

| Table | What it is | Relationship |
|---|---|---|
| `recall_reminders` | "You're due for a cleaning" — sent by an office to a patient **before any appointment exists** | **Parent** of `appointments`, via `appointments.source_recall_id`. Carries `office_id` and `patient_id` directly, so the diagram's office edge is now real |
| `appointment_reminders` | "Your appointment is Tuesday at 2pm" | **Child** of `appointments`, via `appointment_id` — what the doc's script actually built |

This also matches how the data is specified: 2 recalls per patient per benefit year, and 1–3 confirmation reminders per appointment.

```
[ Dental_Offices ] ──┬──→ [ recall_reminders ] ──→ [ appointments ] ──→ [ appointment_reminders ]
                     │              (2 per patient/yr)      │                  (1–3 per appt)
                     └──────────────────────────────────────┘
```

Note that only recall-sourced appointments have a `source_recall_id`; walk-ins and follow-up treatment (3,586 of 6,044 appointments come from a recall) leave it null.

### 2. Insurance networks are now first-class

The doc linked offices to insurance companies directly, with `network_status` chosen at random. Networks are real entities that both sides join, so:

- `insurance_networks` — the 3 networks
- `insurance_company_networks` — each company participates in 1–3 networks
- `office_network_participation` — each office contracts with 1–3 networks
- `office_insurance_network` — **derived**: an office is In-Network with a company when they share at least one network, and `shared_network_id` records which

In-network status is now a consequence of the structure rather than a coin flip, which means it stays consistent for every claim between the same office and payer.

### 3. Benefit accumulators moved from the policy to the patient

The doc kept `individual_deductible_met_ytd` and `family_deductible_met_ytd` on `insurance_policies`. A policy is an employer group covering many families, so a single running total there would have every member of the group sharing one deductible, with no reset between years.

`patient_benefit_years` now holds deductible and annual-maximum consumption **per patient, per benefit year**. Claims draw the maximum down in service-date order, and once it is exhausted the remaining claims that year are denied `Max Benefit Exceeded` — which is how the real failure mode shows up in the data.

## How the money works

Per invoice line:

```
contractual_writeoff       = standard_fee − allowed_amount        (in-network only)
deductible_applied         = drawn from the patient's benefit year, non-preventive only
estimated_insurance_amount = (allowed − deductible − copay) × coinsurance,
                             capped at the patient's remaining annual maximum
estimated_patient_amount   = allowed_amount − estimated_insurance_amount
patient_balance            = estimated_copay_due − actual_patient_paid_at_visit
```

Coverage follows the standard dental split: **preventive 100%, basic 80%, major 50%**, deductible waived on preventive.

## What the data looks like

Verified after generation — all requirement, foreign-key, and consistency checks pass:

| Property | Value | Real-world reference |
|---|---|---|
| Appointment status | 86.6% completed, 9.0% no-show, 4.5% cancelled | — |
| No-show concentration | worst 18% of patients cause 73% of no-shows | research says 60–70% |
| Claim denial rate | 14.9% | industry 10–20% |
| Appeals overturned | 67% | ~69% |
| Mean days to adjudicate | 37.6 | 14–45 by payer |
| Seasonality | December highest (610 visits), February lowest (421) | annual maximums expire in December |

**One deliberate departure from reality:** 17% of denials are appealed here, against a real-world figure closer to 1%. At 1% the `claim_disputes` table would hold about 8 rows, which is useless for modelling. A staffed group practice appealing 17% is defensible, but the rate is a single constant in the generator if you want the harsher number.

## Known limitations

- Procedure descriptions in `billing_codes` are plain-language, **not** ADA nomenclature, which is copyrighted. The CDT code numbers themselves are facts and are real.
- Fees are plausible commercial UCR amounts, not calibrated against a published fee schedule. Real Medicaid allowed amounts for 325 CDT codes are available in the workshop repo at `doc/project-3/data/cdt-medicaid-allowed-amounts.csv` if a calibrated version is wanted.
- Every patient belongs to exactly one office; there is no cross-office movement inside the group.
- No secondary insurance, no coordination of benefits, and no capitation (DHMO) payment path — DHMO companies exist but adjudicate like PPO.
